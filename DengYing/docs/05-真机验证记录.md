# 05 真机验证记录

真机：**vivo V2419A，Android 16（API 36）**，分辨率 1216×2640，density 560。
日期：2026-10-17。安装方式：`adb install -r`（debug 变体，包名 `com.dengying.player.debug`）。

## 1. 首轮：启动即「网络异常，请检查连接」

### 1.1 现象

启动应用，首屏内容区显示：`😕 网络异常，请检查连接` / `点击重试`，
分类 Tab 与顶栏正常渲染。同时顶栏被状态栏遮挡（「灯影」被时钟盖住）。

### 1.2 定位过程（按诊断纪律：先建反馈回路，再假设）

| 步 | 动作 | 观察 | 结论 |
|---|---|---|---|
| 1 | `adb logcat --pid=<app>` 全量抓取 | 应用进程日志中 **零条 `DY/`** | `DengYingApp.onCreate` 从未执行 |
| 2 | `adb shell ping jyzyapi.com` | 通（解析到 28.0.3.70） | 排除"设备无网" |
| 3 | `aapt2 dump xmltree AndroidManifest.xml` | `<application>` **无 `android:name`** | **根因确认** |
| 4 | 检查 `DengYingApp.get()` | `requireNotNull(instance)` 抛异常 | 与步骤 1 互相印证 |

**因果链**：清单漏写 `android:name` → `DengYingApp` 未执行 → `instance` 为 null →
`DengYingApp.get()` 抛 `IllegalArgumentException` → `IndexViewModel.loadData()` 的
`catch (e: Exception)` 把它显示成「网络异常，请检查连接」。

**为什么绕了远路**：那个 catch 把所有异常都说成网络问题，把一次**编程错误**伪装成
**网络故障**。这是本次最有价值的教训。

### 1.3 修复

| 文件 | 改动 |
|---|---|
| `AndroidManifest.xml` | 补 `android:name=".DengYingApp"` |
| `DengYingApp.get()` | 异常消息直指清单与查法；改用 `IllegalStateException` 使调用方可区分 |
| `IndexViewModel.loadData` | 按异常类型分流：装配错误 → 「应用初始化失败」；其余 → 网络提示 |
| 6 个页面根容器 | 补 `WindowInsets.statusBars` 避让（顶栏遮挡） |
| `DetailScreen` 顶栏 | 用 `statusBarsPadding()` 让品牌色延伸到状态栏 |

### 1.4 修复后实测

## 2. 第二轮：选集按钮点不动

### 2.1 现象

详情页点击「正片」选集按钮**无反应**；同一屏内的收藏按钮与线路 chip 都能点中。

### 2.2 定位

对照实验：同一套坐标下，收藏键生效、线路 chip 生效，**只有网格项不生效**。
→ 指向网格自身的可点击区域问题，而非坐标偏差。

**根因**：`LazyVerticalGrid(userScrollEnabled = false)` 嵌在 `verticalScroll` 里。
外层滚动容器拦截手势，而 Lazy 网格自己又不滚动，点击事件到不了项上。

### 2.3 修复

改用**手动按 4 列分行**的普通 `Row`/`Box`。选集数量有限（实测 1 集，长剧最多几百集），
且外层已是 Scroll，嵌套 Lazy 本无收益。

### 2.4 补充：坐标点击不可靠，已建坐标无关通道

后续排查发现 `adb shell input tap` 猜坐标的做法**会产出错误结论**：
详情页版式随「其他资源站」从「查找中…」变为「N 个」而整体位移，
同一次坐标点击在不同时刻命中不同控件，把「按钮坏了」与「我没点中」混为一谈。

为此加了 `DebugPlayReceiver`（仅 debug 源集）：广播
`com.dengying.player.DEBUG_PLAY` 直接进播放页，验证不再依赖坐标。

**但真机上这条通道也没走通**：`am broadcast` 返回 `result=0`，
应用私有目录未生成探针文件——vivo 拦截了外部广播投递。
最终采用**用户手动操作 + 读探针文件**的方式取得证据，这也是后面几轮的验证手段。

## 3. 第三轮：播放页黑屏

### 3.1 现象

用户反馈：进播放页后**全黑无画面**。

### 3.2 定位（探针文件给出完整链路）

```
[detail-playEpisode] idx=0 name=正片 urlLen=35 vodId=93547 source=jyzy
[view-factory]       engine=true boundPlayer=true      ← 绑定成功，不是绑定问题
[resolve-enter]      len=35 source=jyzy vodId=93547
[skip-resolveSharePage] directSource=true
[skip-loadVariants]  directSource=true
[before-probe]       urlLen=35
[after-probe]        elapsed=3042 m3u8=true seg=false host=https://hd.kuktxu.com
[probe-failed-switching]                                ← 探测判分片不可达，去换线
```

**排除了三个嫌疑**（都有探针证据）：
- 不是绑定问题：`view-factory boundPlayer=true`
- 不是短路缺失：`skip-resolveSharePage` / `skip-loadVariants` 都生效
- 不是解码问题：播放器从未报错

**真根因**：`probeReachability` 的分片探测**误判**。它带
`Range: bytes=0-1023` 请求分片，只认 200/206；而部分 CDN 对该请求返回
416 或忽略 Range 返回 200 空体 → **可播的分片被判成不可达** →
应用放弃播放、反复换线 → 用户看到长时间黑屏。

**交叉验证**：用户随后手动操作，**画面出来了**——证明该地址确实可播，
`seg=false` 是误判而非事实。

### 3.3 修复（三处）

| 文件 | 改动 | 理由 |
|---|---|---|
| `HlsUtil.headOk` | 去掉 `Range` 头；判定放宽为 **2xx 即可达** | 消除误判源 |
| `PlayerViewModel.resolveUrl` | 探测不可达时**仍先交给播放器试播**，不再直接换线 | 探测是辅助诊断，不是准入条件 |
| `PlayerViewModel.autoSwitchLine` | 候选判定放宽为**清单可达即用** | 同理，避免误杀可播候选 |
| `PlayerViewModel.onError` | 新增 `switchLineOnPlaybackError`：**播放器真实报错才换线** | 解码器说不行才是真的不行；比探测猜准确 |

## 4. 第四轮：全屏后锁死横屏，返回不恢复

### 4.1 现象

用户反馈：全屏之后应用**一直是横屏**，点击返回也不恢复。

### 4.2 定位（三个独立缺陷叠加）

| # | 缺陷 | 后果 |
|---|---|---|
| 1 | 恢复逻辑写在 `DisposableEffect(Unit) { onDispose { ... } }` 里 | 该 `onDispose` 只在 **NavHost 整体离开组合**（Activity 销毁）时触发。返回键退出播放页时 NavHost 仍在 → **恢复代码从不执行** |
| 2 | `preFullscreenOrientation` 是 Composable 局部状态 | 播放页一离开组合即丢弃；下次全屏读到的是已变横屏的值，"恢复"等于没恢复 |
| 3 | 未实现"全屏时返回键先退全屏" | 沉浸态下系统栏不可见，缺少页面内出口；原工程 `onBackPress` 有此语义 |

### 4.3 修复：照成熟实现重写（关键转折）

初版修了三处（控制器化、返回键、快照），**用户复测仍锁死横屏**。于是不再自己摸索，
去查开源壳子的实现，找到 [fengdai/compose-media 的 FullscreenToggle.kt]
(https://github.com/fengdai/compose-media/blob/master/sample/src/main/java/com/github/fengdai/compose/media/sample/FullscreenToggle.kt)
（Compose 媒体播放库的官方示例）。对比后发现初版有**三处根本性错误**：

| # | 初版做法 | 成熟做法 | 后果 |
|---|---|---|---|
| 1 | 自己维护 `isFullscreen` 布尔 + "进入前方向快照" | **`requestedOrientation` 是唯一真相**，UI 从 `LocalConfiguration.orientation` 反推 | 布尔与真实方向脱节后，恢复逻辑再也对不上 → **锁死横屏的根因** |
| 2 | 退全屏"恢复快照" | 退全屏**显式回竖屏**（`USER_PORTRAIT`） | 快照若本就是横屏，"恢复"等于保持横屏 |
| 3 | `BackHandler(enabled = 普通字段)` | `OnBackPressedCallback` + `SideEffect { isEnabled = isLandscape }` | 普通字段不触发重组，`enabled` 恒为初值 `false` → **返回键从未被接管** |

另有一处取值修正：方向用 `USER_LANDSCAPE` / `USER_PORTRAIT` 而非 `SENSOR_*`。
`SENSOR_*` 会跟随重力翻转（躺着看画面会跟着转），`USER_*` 尊重系统自动旋转开关，
这是播放器的通行做法。

**设计要点**：不自己维护"是否全屏"。`SideEffect` 每次成功重组都把方向与系统栏
对齐到当前形态——这一步是**自愈**的关键，不依赖任何一次点击是否成功。
旋转、Activity 重建、系统栏变化都能收敛回正确状态。

### 4.4 复验（通过）

轮询 `dumpsys window displays` 记录方向轨迹，用户手动操作：

```
T+5s .. T+50s   mCurrentAppOrientation=SCREEN_ORIENTATION_USER_PORTRAIT   mCurrentRotation=ROTATION_0
T+55s           mCurrentAppOrientation=SCREEN_ORIENTATION_USER_LANDSCAPE  mCurrentRotation=ROTATION_90   ← 点全屏
T+60s           mCurrentAppOrientation=SCREEN_ORIENTATION_USER_PORTRAIT   mCurrentRotation=ROTATION_0    ← 按返回
```

对比修复前（卡在 `SENSOR_LANDSCAPE` / `ROTATION_90` 不动）：
**退出全屏后回到 `USER_PORTRAIT` / `ROTATION_0`，不再锁死**。

另注：`T+5s` 时方向已是 `USER_PORTRAIT`（非手动设定），说明进入播放页时
状态同步机制即在工作——这正是"系统方向为唯一真相"带来的效果。

## 6. 验证方法论（本轮最重要的产出）

**vivo 的 ROM 会全量过滤第三方应用日志**——`Log.i`、`Log.w` 都读不到
（`adb logcat -d | grep DY/` 只偶发命中）。这让"看日志排查"完全失效。

最终可靠的手段是**探针文件 + 用户手动操作**：

```bash
adb shell run-as com.dengying.player.debug cat files/playback.log
```

`PlaybackProbe` 把关键状态迁移写到 `files/playback.log`，
只写状态名与布尔/长度（不写完整地址，SEC-004 同一口径）。

**另外两条教训**：

1. `adb shell input tap` 猜坐标**不能作为验证手段**——版式会变，
   坐标点击的失败无法区分"控件坏了"与"没点中"。为此浪费了多轮往返。
2. **修一处要回归相邻路径**。本轮有 5 个新缺陷是在修另一个缺陷时引入的，
   且直到用户反馈才发现。探针日志能立刻暴露"同一地址被反复 startEngine"这类异常模式，
   应养成"改完先看探针"的习惯。



## 3. 为真机验证补的观测通道

### 3.1 问题

vivo 的 ROM **全量过滤第三方应用的日志**——`Log.i`、`Log.w` 都读不到
（`adb logcat -d | grep DY/` 只偶发命中一行）。靠日志排查播放链路不可行。

### 3.2 处置：写文件探针

`PlaybackProbe`（`playback/PlayerFactory.kt`）把关键状态迁移写到应用私有目录
`files/playback.log`，用 `adb shell run-as <pkg> cat files/playback.log` 读回。
观测点：`setMedia` / `STATE_READY` / `STATE_BUFFERING` / `STATE_ENDED` /
`VIDEO_SIZE` / `PLAYER_ERROR`，以及解析链的 `resolve-enter` / `SEC005-reject` / `probe`。

**只写状态名与布尔/长度，不写完整地址**（SEC-004 同一口径）。

### 3.3 处置：坐标无关的触发入口

`DebugPlayReceiver`（**仅 `src/debug` 源集**）接受广播
`com.dengying.player.DEBUG_PLAY`，直接构造播放路由交给 `MainActivity`。

存在的理由：详情页版式会随「其他资源站」从「查找中…」变为「N 个」而整体位移，
同一次坐标点击在不同时刻命中不同控件——这会让「按钮点不动」与「坐标没命中」
两类结论混淆，无法区分。

**隔离已验证**：`aapt2 dump xmltree` 核对 release APK，不含 `DebugPlayReceiver`
与 `DEBUG_PLAY` action。

**是正常行为**：该次拖动过程中列表触底触发了 `loadMore`，`n` 从 41 变为 81，
而 `idx` 是按**拖动当刻的 `n`** 换算的，故 36 对应的是 41 项列表的第 37 项位置。
改用单次 tap（精确单事件、`n` 不变）复测：底部 → `idx=80 n=81` = n-1，
正中 → `idx=40 n=81`，**几何换算正确**。

**这一条值得记住：验证几何换算必须用单事件（tap），拖动的中间态会被并发状态变更污染。**

### 9.4 缺陷：手动 seek 被「续播恢复」覆盖

**现象**（探针 `files/playback.log`，`adb shell run-as com.dengying.player.debug cat files/playback.log`）：

```
492 [engine-seek] target=3245598        ← 用户手动 seek 到 54:31
494 [STATE_READY]
497 [engine-ready]
498 [resume-restore] ep=0 pos=3271638   ← 续播恢复把位置改回去了
499 [engine-seek] target=3271638
```

两次复现（第一次被拉回 1:55，第二次被拉回 54:31），中间无其他用户操作。

**根因（两处，互相独立，各自都足以造成覆盖）**：

1. `ui/src/commonMain/kotlin/com/dengying/player/ui/viewmodel/DetailViewModel.kt` 的
   `toFullscreen()` 构造 `Routes.player(...)` 时**漏传 `startAtMs` 与 `headersJson`**，
   而同一文件的 `playEpisode()` 正确传了。漏传导致 `restorePosition()` 的第一道守卫
   `if (params.startAtMs > 0) return` 失效 —— 内嵌播放切全屏是被丢进
   `PlayerViewModel` 的新实例（`viewModel(key="player_${source}_${vodId}_${episodeIndex}")`），
   新实例手里没有「用户刚刚看到哪一帧」，只能退回历史记录。
2. `ui/src/commonMain/kotlin/com/dengying/player/ui/viewmodel/PlayerViewModel.kt` 的
   `onDrag()` / `onDragEnd()` **没有置位 `manualSeekOccurred`**（只有 `onDragStart()` /
   `onSeekStart()` 置位）。真机上 `Slider` 自己消费拖动手势，
   外层 `pointerInput { detectTapGestures(onPress = …) }` 不保证收到按下信号 → 守卫形同虚设。

**修法**：

- `toFullscreen()` 补传 `startAtMs = s.curTime` 与 `headersJson = s.headers`。
- `onDrag()` / `onDragEnd()` 各自开头补 `manualSeekOccurred = true`。
- 把判定从 `restorePosition()` 里搬成纯函数
  `shared/src/commonMain/kotlin/com/dengying/player/domain/playback/ResumeRestore.kt`：
  `shouldLoad(startAtMs, vodId, source, alreadyRequested)` 与
  `apply(storedMs, manualSeekOccurred, headGuardMs)`，各自返回带 `reason` 的结论。
  搬出来的理由：判定与 Android 无关，混在协程 + 磁盘 IO 里就只能靠跑真机看日志确认，
  而真机观察又受网络与版式位移干扰——这正是本次排查反复绕圈的原因。
- 探针 `resume-restore-check` 补记 `load=… why=…`，四个早退分支从此可区分。

### 9.8 新缺陷：历史直达播放后返回详情页，内嵌位不恢复（会话状态未登记）

**现象**（2026-10-31 真机，复现 ≥2 次）：播放历史点入 → 自动跳转全屏播放页（FR-506）→
播放中按返回 → 详情页内嵌位显示「选择下方剧集开始播放」占位，不恢复播放。
同一构建下「内嵌播放 → 点全屏 → 返回」路径正常（`[inline-resumed]` 出现）。

**根因（探针钉死）**：历史直达路径里 PlayerViewModel 自己起播
（`startEngine → setMedia` 直连引擎，见 §9.4 复验日志 L14-15），**不经过
`PlaybackSession.play`**，单例会话状态保持 `Idle/urlEmpty`。返回详情页时
`resumeInlineIfPlaying()` 的 `if (!s.hasSession) return` 命中 → 静默退出。
探针证据（2026-10-31 加装 `inline-resume-skip` 两处早退探针后复现）：

```
[inline-hidden-cleared]
[inline-resume-skip] reason=no-session status=Idle urlEmpty=true   ← 当时引擎实际在播
[engine-pause-call]
```

**连带症状（同一根因）**：

- 详情页无内嵌会话时点「全屏」键：`toFullscreen()` 的 `if (!s.hasSession) return`
  在探针**之前**静默早退（无 `inline-to-fullscreen`），按键看似无效；
