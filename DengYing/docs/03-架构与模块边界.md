# 03 架构与模块边界

## 1. 组件与职责

| 组件 | 职责 | 目录 | 公开契约 | 隐藏细节 | 依赖约束 |
|---|---|---|---|---|---|
| **core** | 全局契约与常量：领域模型（`VideoItem`/`CmsClass`）、源协议类型（`CmsSource`/`SourceCaps`/`FetchResult`/`PlayResolveResult`/`WebRule`）、四态判定（`RequestOutcome`）、源清单（`CmsSources`）、密钥、日志标签 | `core/` | 上述 data class / enum / object | 各源的 host 与路径常量、CAPS 组合 | **不得**导入 `android.*` / `androidx.*` / `com.dengying.player.{data,ui,playback,app,domain}` |
| **domain** | 平台无关的业务不变式，按关注点分子包（见 §1.1） | `domain/{page,playback,search,source,store,ui}/` | 各 object/class 的公开函数与 data class | 内部比较器、常量、正则 | **不得**导入 `android.*` / `androidx.*` / `com.dengying.player.{data,ui,playback,app}` |
| **data.net** | 唯一出网口（`HttpClient`）、HLS 解析与探测 | `data/net/` | `HttpClient`、`HlsUtil` | 连接复用策略、UA 常量 | 可依赖 `core` + `domain`，不得依赖 `ui` |
| **data.source** | 源聚合编排与协议适配器、签名/加密 | `data/source/` + `adapters/` + `crypto/` | `SourceRepository`、各 Adapter | 各适配器的 URL 拼装、字段路径 | 可依赖 `core` + `domain` + `data.net`，不得依赖 `ui` / `data.store` |
| **data.store** | 个人资产与设置落地 | `data/store/` | `Store` 的读写函数（全部 `suspend` 或显式 `Blocking`） | 键名、信封编码、同步/异步边界 | 可依赖 `core` + `domain` + `org.json`，不得依赖 `ui` |
| **playback** | Media3 封装与会话编排 | `playback/` | `Engine` 窄接口、`EngineListener`、`PlaybackSession` | ExoPlayer 类型、缓冲参数、数据源工厂 | 可依赖 `androidx.media3` + `data`，不得依赖 `ui` / `app` |
| **ui** | Compose 页面、组件、主题、ViewModel | `ui/{pages,components,viewmodel,navigation,platform,theme}/` | 各 `Screen` Composable（参数即契约）；ViewModel 构造函数（依赖即契约） | ViewModel 内部状态机 | 可依赖全部下层 + `app`（仅页面层取组合根）；**下层不得反向依赖** |
| **app** | 组合根：装配 store / sources / pageCache | `app/` | `DengYingApp.get()` | 初始化顺序 | 只依赖 `data.source` + `data.store` |

### 1.1 `domain` 的子包划分

23 个纯逻辑文件平铺在一个目录里，找「分页策略」要逐个点开。按关注点分组后，一个子包 = 一个可独立说明的职责：

| 子包 | 文件 | 共同点 |
|---|---|---|
| `domain/page/` | `PageCacheRules`、`PageBudget`、`ConcurrencyGate`、`ListBatch` | 首页分页的缓存、预算、并发与批次 |
| `domain/playback/` | `CastUtil`、`GestureRules`、`HlsVariants`、`ResumeDecide`、`SeekPreview` | 播放器的纯判定 |
| `domain/search/` | `SearchSession`、`SearchNotice`、`TitleKey` | 搜索会话与跨源折叠 |
| `domain/source/` | `SourceHealthRules`、`SourceOverrideRules` | 源健康与启用覆盖 |
| `domain/store/` | `FavoritePrune`、`LedgerPrune`、`StoreEnvelope`、`StoreGate` | 本地数据策略 |
| `domain/ui/` | `ConfirmSpec`、`UrlGuard`、`TouchTarget` | UI 层的纯规则 |

### 1.2 `ui/components` 的玻璃控件分层

`GlassBackdrop.kt`（背景采样状态）与 `GlassSurface.kt`（玻璃面 / 胶囊）、`GlassFx.kt`、
`DyIcons.kt`（纯 `Path` 矢量图标）是视觉原语；`GlassControls.kt` 把**页面级交互件**收口成
`GlassCircleButton` / `GlassBackButton` / `GlassClearButton` / `GlassTextField` /
`GlassActionButton` 五种原子件，统一 44dp 热区、48dp 输入/按钮等高与 `liquid=false`
静态玻璃口径。搜索、登录、注册、我的与全部二级页只传文案和事件，不再各写一份
`OutlinedTextField` 配色、裸返回箭头或墨色实底按钮。

海报卡（`IndexScreen.RailCard` / `VideoCard` / `DiscoverVideoCard`、
`SearchScreen.ResultRow`）同样只用 `GlassSurface(liquid = false)`：只有导航件和播放器
控制层开实时透射，全屏几十张卡采样会把滚动帧率拖穿（见 `GlassBackdrop.kt` 注释）。
`CommonUi.kt` 继续只放跨两个以上页面复用的状态视图，不吸收这些视觉原语。

**采样层与玻璃件的结构约束（v1.2.8 定案，踩过两次坑）。** 实时透射要求玻璃采样
「它背后真正在画的内容」，Compose 里唯一可行的做法是把那段内容录进 `GraphicsLayer`
再 `drawLayer`。这里有一条硬约束：**采样图层不能包含玻璃件自己**——玻璃件
`drawLayer(采样层)` 若采样层里有它，就是自引用递归，RenderThread 直接栈溢出
（实测 `SIGSEGV` / `stack pointer is not in a rw map` / 512 帧）。因此：

- `GlassPageBackdrop.kt` 提供 `GlassPage(modifier, content, overlay)`，结构固定为
  `Box { Box(采样层){ content() } ; overlay() }`——内容层被录制，玻璃件全部放 overlay，
  两者是**兄弟**。首页顶栏与 Dock、搜索栏、收藏/历史/源状态顶栏走这条路径。
- 页面没有玻璃 overlay 时用 `Modifier.glassPageBackdrop()`，图层里**只录柔光渐变**，
  天然不含玻璃件（登录/注册/我的/详情）。
- `LocalGlassInSampledContent` 是保险：`GlassPage` 把 content 子树标记为「在采样层内」，
  `GlassSurface` 见到这个标记就强制走静态分支。否则内容里偶然长出的
  `liquid = true` 玻璃件会绕过结构约束，把「漏审」变成闪退。
- `backdrop.layer` 必须在**绘制期**赋值而非组合期：从 B 页返回 A 页时 A 不重组，
  组合期赋值会让 state 停在已释放的 B 图层。谁这一帧在画，谁就是采样源。

详情页（`DetailScreen`）刻意不用 `GlassPage`：内容区含内嵌播放位，`SurfaceView`
不参与图层合成，录进去也采不到画面，收益为零而崩溃风险在。

### 1.3 `core` 为什么独立存在

改动前 `FetchResult` / `CmsSource` / `WebRule` 这些**契约类型**埋在 `data/source/SourceTypes.kt`，
而 `ui` 层直接 import 它们——那是 data 层反过来定义 UI 依赖的形状，层与层之间穿透了。

`RequestOutcome` 的归属更糟：它原先在 `domain/source/`，但 `FetchResult` 持有 `RequestOutcome`
字段，于是 **data 依赖 domain**——契约反过来依赖上层策略。现在两者同在 `core/`。

把这些类型收进 `core` 后，`data` 与 `ui` 都只依赖 `core`，彼此不再互相穿透；`RequestOutcome`
本身零 import（纯类型 + 纯函数），下沉不带来任何连带依赖。

### 1.3 投屏通道的模块边界（PR #6 / FR-418..423）

投屏是唯一把「平台专用第三方 SDK」接进播放页的能力，边界按下面三层切开：

| 层 | 文件 | 允许依赖 | 不得做什么 |
|---|---|---|---|
| 契约（`:shared/commonMain`） | `playback/cast/CastController.kt`：`CastController` 接口、`CastDevice` / `CastMedia` / `CastEvent` / `DisconnectCause`、`NoopCastController` | `kotlin.*` + `domain/playback/CastUtil`（复用失败分类口径） | 不得出现 `android.*` / `androidx.*` / `com.google.android.gms.*`；不得把 `Context`、GMS 类型放进签名 |
| 编排（`:ui/commonMain`） | `PlayerViewModel`：`onCastClick` / `onCastDeviceSelected` / `dismissCastSheet` / `onCastEvent` / `onCastDisconnected`；`PlayerScreen`：设备选择面板 | `:shared` + CMP；`CastController` 经构造函数注入 | 不得 `new` GMS 类、不得摸 `DengYingApp.get()`；失败文案一律走 `CastUtil` |
| 实现（`:app`） | `DengYingCastOptionsProvider`（`OptionsProvider`）、`GmsCastController`（`CastContext` / `MediaRouter` / `SessionManager` / `RemoteMediaClient`）；`UiDeps.castController` 注入 | AndroidX `mediarouter` + `play-services-cast-framework` | 不得让 `playback/cast` 反向依赖 `:app` 或 `:ui` |

**为什么用 interface 而不是 expect/actual**：与 `PlayerEngineHost` / `UiDeps` 同理由——
这是装配关系，不是「同一件事在各平台有不同实现」的平台服务。Android 注入 GMS 实现，
其它平台注入 `NoopCastController`（`isAvailable() == false`，UI 据此禁用入口），
不需要为每个 target 写一份 `actual`，也不会把 GMS 类型泄漏进 `commonMain`。

**Manifest 与依赖**：`app/src/main/AndroidManifest.xml` 登记
`com.google.android.gms.cast.framework.OPTIONS_PROVIDER_CLASS_NAME` → 真实类
`DengYingCastOptionsProvider`；`play-services-cast-framework:23.0.0` 只加在 `:app`
（版本目录 `playServicesCastFramework`）。`cast-framework` 的 POM 传递
`androidx.mediarouter:1.9.0-beta01`，用 `resolutionStrategy.force` 锁回 1.8.1。
口径变化（引入 GMS）与体积评估见 `docs/01 §1.1`。

## 2. 依赖方向

```
        ┌──────────────────────────────────────────────────────┐
        │ ui (pages / components / viewmodel / nav / platform) │
        └───────┬───────────────────────────────┬──────────────┘
                │                               │
        ┌───────▼───────┐              ┌────────▼─────────┐
        │ playback      │              │ app (组合根)      │
        │ (Media3 封装)  │              │ DengYingApp      │
        └───────┬───────┘              └────────┬─────────┘
                │                               │
        ┌───────▼───────────────┬───────────────▼─────────┐
        │ data.cache            │ data.store              │
        │ data.source ─> data.net                         │
        └───────┬─────────────────────────┬───────────────┘
                │                         │
        ┌───────▼─────────────────────────▼───────────────┐
        │ domain (page/playback/search/source/store/ui)   │
        │ 零 Android 依赖                                  │
        └───────────────────┬─────────────────────────────┘
                            │
        ┌───────────────────▼─────────────────────────────┐
        │ core (契约类型 + 常量，零 import)                │
        └─────────────────────────────────────────────────┘
```

`app` 画在 `ui` 下方而非上方，是因为依赖方向是 **`ui.pages` → `app`**（页面层取组合根装配
ViewModel），而 `app` 只依赖 `data`。这一条是刻意保留的：`app` 不该反向依赖 `ui`（那会成环），
而 ViewModel 也不该摸全局单例（否则 JVM 单测没法构造它）。页面层是唯一同时看得见两侧的地方。

**硬约束（可 grep 验证）**：

```bash
# domain 不得出现 Android 类型
grep -rn "^import android\|^import androidx" app/src/main/java/com/dengying/player/domain/   # 必须无输出

# data / playback 不得反向依赖 ui
grep -rn "^import com.dengying.player.ui" app/src/main/java/com/dengying/player/data/ app/src/main/java/com/dengying/player/playback/   # 必须无输出

# core 不得依赖任何上层
grep -rn "^import com.dengying.player.\(data\|ui\|playback\|app\|domain\)" app/src/main/java/com/dengying/player/core/   # 必须无输出

# domain 不得依赖 data / ui / playback / app
grep -rn "^import com.dengying.player.\(data\|ui\|playback\|app\)" app/src/main/java/com/dengying/player/domain/   # 必须无输出

# ViewModel 不得反向依赖页面与组件
grep -rn "^import com.dengying.player.ui.\(pages\|components\)" app/src/main/java/com/dengying/player/ui/viewmodel/   # 必须无输出

# playback 不得依赖组合根与 UI
grep -rn "^import com.dengying.player.\(app\|ui\)" app/src/main/java/com/dengying/player/playback/   # 必须无输出
```

## 3. 模块边界的三处取舍（都写清理由）

### 3.1 为什么只有一个 Gradle module

本工程用**包**而不是**构建模块**划边界。理由：

- 依赖图是直线，没有"某模块只在 debug 变体里存在"这类需求；
- 拆 `:domain` 模块会让它的单元测试也能享受 JVM 隔离，但**同一个 `:app` 模块的 `src/test` 已经是纯 JVM**，
  收益为零；
- 拆模块的代价是增量编译变慢、`./gradlew` 命令变长、IDE 跳转变多一次模块边界。

**代价要诚实说明**：包边界靠**人工审查 + 上面六条 grep**，不靠编译器。
写错一个 `import` 编译器不会拦。若将来需要机器强制，可加 `lint` 的
`KotlinPropertyAccess` 自定义规则或 `kotlin-architecture-test` 库——本次不引入新依赖（SEC-001）。

### 3.2 为什么 `domain` 允许 `org.json`

`StoreEnvelope` 与 `SourceOverrideRules` 需要判定"这串文本是数组、信封还是损坏"。
自己写一个 JSON 解析器换来的"零依赖"，代价是**它自己成为需要测试的代码**，收益为负。

- Android 运行时内置 `org.json`，**不增加 APK 依赖**；
- JVM 单测由 `testImplementation("org.json:json")` 提供真实现（否则会撞上 `not mocked` 桩）。

故这条豁免写在 `StoreEnvelope` 的文件头注释里，是有意识的例外，不是疏忽。

### 3.3 为什么 `HttpClient` 用 `HttpURLConnection` 而不是 OkHttp

SEC-001 要求"不接入第三方 SDK"。`HttpURLConnection` 满足全部需要：
自定义头、逐请求超时、二进制收发、状态码、禁用重定向。
OkHttp 的连接池复用对"多源并发 + 每个源独立主机"的负载收益有限，
而代价是引入一份第三方依赖及其线程池、拦截器栈、证书固定等自带行为。

`HttpURLConnection` **并非"每个请求新建 TCP 连接"**——这条曾写在文档里，是错的。
实测（`HttpClientConnectionReuseTest` / `HttpClientConnectionReuseDeviceTest`，
判据是本地服务端的 `accept()` 次数）：连续 3 次 GET 同一主机，

- JDK 18：只 `accept` **1** 次
- Android 16（SDK 36，V2419A）：同样只 `accept` **1** 次

即系统栈自带 keep-alive 池，连接默认就被复用。机制是 `stream.use { }` 关闭流那一刻
连接已还回池；之后再 `disconnect()` 拿不回池里的连接，是空操作。

由此两条推论，都别再重走弯路：

1. **「删掉 `finally` 里的 `disconnect()` 以启用连接复用」是伪优化**——收益为零，
   只增加复杂度。该改动曾落地，实测后已回退。
2. 保留无条件 `disconnect()` 的**唯一理由**是兜底未读干净的响应体：3xx 无
   `errorStream`、读一半抛异常时，这条带残渣的 socket 必须丢弃，否则下一个请求
   会先读到垃圾。这条由上述测试的 `unreadableRedirectBody*` 用例锁住。

在 29 个源并发、每源 1-2 个请求的规模下，真正的网络开销不在握手，而在
**响应体读取的缓冲区与预分配**（见 §3.4）。若将来实测发现握手真成瓶颈，
换 OkHttp 的改动面仍是 `HttpClient` 一个文件。

### 3.4 响应体读取：缓冲区与预分配

`HttpClient` 与 `Poster` 读响应体时的两个参数直接决定系统调用次数与内存拷贝次数：

- `IO_BUFFER = 32 KiB`（`copyTo` 默认 8 KiB）。源站 JSON 常 50-500 KB，
  8 KiB 意味着上百次 `read`；提到 32 KiB 把系统调用压到约 1/4。
- 按 `conn.contentLengthLong` 预分配 `ByteArrayOutputStream`，上限
  `MAX_PRESIZE = 4 MiB`。默认构造从 32 字节起步、倍增扩容，等于把同一份数据
  复制好几遍。gzip 透明解压时 `contentLength = -1`（长度未知），以及超过 4 MiB
  的响应（防坏头撑爆内存），都退回默认策略。

## 6. ViewModel 的依赖从哪来

改造前 7 个 ViewModel 全部写 `private val store get() = DengYingApp.get().store`。
后果是**没法单独构造一个 VM**——任何 VM 测试都必须先把整个 `Application` 跑起来，
而这在 JVM 单测里做不到（`Application` 需要 Android 运行时）。

现在的形状（以 `IndexViewModel` 为例）：

```kotlin
class IndexViewModel(
    private val repo: SourceRepository,
    private val cache: PageCache,
) : ViewModel() { ... }
```

页面层是唯一同时看得见「组合根」和「VM」的地方，装配落在那里：

```kotlin
vm: IndexViewModel = run {
    val deps = DengYingApp.get()
    androidx.lifecycle.viewmodel.compose.viewModel(
        factory = object : androidx.lifecycle.ViewModelProvider.Factory {
            @Suppress("UNCHECKED_CAST")
            override fun <T : ViewModel> create(modelClass: Class<T>): T =
                IndexViewModel(repo = deps.sources, cache = deps.pageCache) as T
        },
    )
},
```

`PlaybackSession.play(...)` 同样收 `repo` 参数，不再自己 `DengYingApp.get().sources` ——
否则 `playback` 会反向依赖组合根 `app`，那是结构性的倒挂。

**为什么仍不引入 Hilt/Koin**：全应用只有 3 个长生命周期对象（`Store`、`SourceRepository`、
`PageCache`），显式装配比框架更清楚，且启动更快（见 `DengYingApp.kt` 的 KDoc）。
构造函数注入解决的是「VM 不摸全局」，不是「需要容器」。

**一条刻意的例外**：`PlayerViewModel.onCleared` 用裸 `Thread` 写一次历史。
那里 `viewModelScope` 已被取消，而 FR-408 要求"离开立即落盘"。
`SharedPreferences.commit()` 本身同步，故用独立线程避免阻塞主线程；这是全工程唯一的裸线程。
