# 01 移植说明

| 属性 | 内容 |
|---|---|
| 来源工程 | `hmVideo`（HarmonyOS / ArkTS，包名 `com.dengying.player`） |
| 本工程 | `DengYing`（Android / Kotlin + Compose） |
| 版本 | 1.1.0（versionCode 1000100，与源工程对齐） |
| 层级 | Tier 1 —— 新增平台、跨平台边界、替换平台契约 |
| 日期 | 2026-10-17 |

## 1. 范围

**移植**（行为契约保持，逐条可在源码注释里对照）：

- 领域不变式：标题折叠键、源请求四态、地址校验、存储闸门与版本信封、
  观看记录分组淘汰、收藏容量淘汰、续播直达判定、搜索会话序号、
  页面预算、并发闸门、HLS 变体、源健康分、源覆盖层、可投性判定。
- 源接入：29 个源描述符（18 个 CMS + 11 个多协议）、8 个协议适配器、
  签名与加密原语（MD5/SHA1、AES-CBC/ECB、RSA-PKCS1、Java LCG、protobuf 子集）。
- 页面：首页、搜索、详情、播放、收藏、历史、源状态，共 7 个。
- 存储：收藏 / 观看记录 / 搜索历史 / 自动连播开关 / 源覆盖层 / 分类表缓存。

**不移植**（不是遗漏，是判断）：

| 项 | 理由 |
|---|---|
| 鸿蒙 `EntryBackupAbility` | Android 的备份范围用 `backup_rules.xml` + `data_extraction_rules.xml` 表达，语义等价，不需要额外 Ability |
| `XComponent` + surfaceId 绑定时序 | Media3 的 `PlayerView` 自持 surface，不存在"先 surface 后 url"的约束。复刻一个不存在的约束会制造假依赖 |
| `PlaybackSpeed` 枚举映射 | Media3 的 `PlaybackParameters` 接受任意 float，五档直接可用 |
| `Fullscreen.ets` 的窗口 API 序列 | 换成 `WindowInsetsControllerCompat` + `requestedOrientation`，顺序约束消失（Compose 不重建布局） |
| 投屏的 `AVSessionKit` 链路 | Android 侧改用 **Google Cast 框架（GMS）** 接通真实通道：`DengYingCastOptionsProvider` 提供 `CastOptions`，`GmsCastController` 用 `MediaRouter` 发现设备、`SessionManager` 管会话、`RemoteMediaClient` 下发媒体，断开后回落本机播放。鸿蒙的 `AVCastPicker` 是系统 picker，GMS 侧改用 Compose 自绘设备选择面板，语义等价但实现不复用。原工程的投播链路在真机上也未验证；本次实现同样**未真机验证**。口径变化见 §1.1 |

### 1.1 投屏接入 GMS Cast 后的口径变化（PR #6）

历史文档写过「不接入 Google Cast 云端服务 / 无第三方 SDK 出站」。接通真实投屏通道后，
这条**不再是事实**，如实更正如下：

| 项 | 接入前口径 | 当前口径 |
|---|---|---|
| 第三方 SDK | 只有 AndroidX `mediarouter` | 增加 `com.google.android.gms:play-services-cast-framework:23.0.0`（版本目录 `playServicesCastFramework`） |
| 设备发现 / 会话 | 无 | 由设备上的 **Google Play 服务（GMS Cast 框架）** 承担；`OPTIONS_PROVIDER_CLASS_NAME` 登记真实存在的 `DengYingCastOptionsProvider` |
| 媒体流向 | 无 | 媒体地址经 GMS 会话交给**局域网内**的 Cast 接收端，由接收端自行拉流；本应用不转发媒体字节 |
| 应用自建云端 | 无 | **仍无**：不建服务端、不上报用户数据、不引入账号/埋点/推荐（SEC-001 的产品约束不变） |
| 出站 | 无第三方 SDK 出站 | GMS 框架自身与 Google Play 服务的通信由系统承担，不在本应用网络栈内；本应用所有业务请求仍走统一 `HttpClient` |

**体积与成本评估（SEC-001）**：debug APK 从约 39.3 MB 增至 44.9 MB（+约 5.6 MB，
含 GMS Cast 框架及其传递依赖）；启动时不立即建 `CastContext`（`UiDeps.castController`
用 `lazy`），未点投屏不付这次 GMS 绑定成本。`cast-framework` 的 POM 传递
`androidx.mediarouter:1.9.0-beta01`，`app/build.gradle.kts` 用 `resolutionStrategy.force`
锁回稳定线 1.8.1，不升级无关工具链（Kotlin/CMP/AGP/Gradle 均不动）。

**仍未验证**：GMS 可用性、真实设备发现、会话建立、远端拉流与断开回落都**没有真机或
模拟器证据**（本环境无设备、无 system-image、无 AVD）。见 `docs/04 §3`。

## 2. 与鸿蒙版的逐项差异

### 2.1 语言与框架

| 关注点 | ArkTS | Kotlin |
|---|---|---|
| 空值 | 显式 `| null` + 运行期判空 | 类型系统区分，`String?` 必须处理 |
| 并发 | `Promise` / `async-await` | 挂起函数 + `Mutex` / `CompletableDeferred` |
| 可变状态 | `@State` 装饰器 | `mutableStateOf` + `ViewModel` |
| 单例装配 | 模块级 `let` + 显式 init | `Application` 持有，构造注入 |
| 错误 | `try/catch` 包裹异步 | 同（但 `CancellationException` 需单独处理，见 §2.4） |

### 2.2 平台能力对照

| 用途 | 鸿蒙 | Android | 语义差异 |
|---|---|---|---|
| HTTP | `@ohos.net.http` | `HttpURLConnection` | 均为系统栈；自定义头、逐请求超时、二进制收发一致。不引入 OkHttp（第三方 SDK，违反 SEC-001） |
| 偏好存储 | `@ohos.data.preferences` | `SharedPreferences` | `commit()` 同步返回布尔 → 正好对应 FR-507 的「是否已落盘」 |
| 播放 | `media.AVPlayer` | Media3 `ExoPlayer` | 见 §2.3 |
| 播放渲染 | `XComponent(SURFACE)` | `AndroidView(PlayerView)` | 不暴露 surface 生命周期 |
| 日志 | `hilog`（16 位领域号） | `android.util.Log`（tag） | 领域号折进 tag 前缀 `DY/`，`adb logcat -s DY.*` 可整组过滤 |
| 路由 | `@ohos.router` + `pushUrl({params})` | Navigation Compose + 字符串路由 | 对象通道没了，故补一层显式 URL 编码（`Routes.kt`） |
| 全屏 | `window.setWindowLayoutFullScreen` | `WindowInsetsControllerCompat` | 同 |
| 方向 | `setPreferredOrientation` | `requestedOrientation` | 退出时按快照恢复，不硬设竖屏 |
| 投屏 | `avSession` + `AVCastPicker` | GMS Cast 框架 + Compose 设备面板 | 通道已接通（未真机验证）；`CastUtil` 负责可投性与失败分流 |
| 对话框 | `UIContext.showAlertDialog` | `AlertDialog`（Compose） | 焦点策略改为"取消键是 dismiss 位置" |

### 2.3 播放链路的语义差（最重要的一节）

| 原工程机制 | 本移植 | 影响 |
|---|---|---|
| `setMediaSource(createMediaSourceWithUrl(url, headers))` | `DefaultHttpDataSource.Factory().setDefaultRequestProperties()` | 请求头在**数据源工厂**层注入，HLS 与 progressive 共用同一工厂；FR-402 的"头真实生效"落点更低、覆盖更全 |
| 换集必须 `release` + 重建 | 同样 `release` + 重建 | 保留原行为：换集后要重走"解析 → 探测 → 自动换线"，就地替换媒体源会跳过这条链路 |
| 探测串行 2 次 GET（m3u8 + 首分片） | 同 | 原工程把"探测串行抬高首帧"记为已知代价（R-006），本移植不改变该取舍 |
| `progressively` 每 5 tick 落盘 | 同（1s 一次 `currentPosition`，每 5 次写库） | 保留"恢复位置误差 ≤ 1 个节流周期" |
| 小于 3 秒视为从头 | 同 | FR-405 验收条件 |
| 播完先落盘再切集 | 同 | 顺序错会用新集序号写错历史条目 |

### 2.4 并发语义的差异（容易踩的坑）

原 ArkTS 的 `ConcurrencyGate` 用 Promise 队列实现；Kotlin 侧用 `Mutex` + `CompletableDeferred`。
**三处必须保持的行为**：

1. **FIFO 唤醒**：后到的短任务不得插队（否则先到的长任务饿死）。
2. **重复释放不放大上限**：`release()` 在 `active == 0` 时静默忽略，否则计数变负会让上限翻倍。
3. **`cancelQueued()` 只丢弃排队中的**，已在跑的不动——半途掐断一个正在读的响应没有安全收尾方式。

另外 Kotlin 侧新增一条原工程没有的处理：`CancellationException` 必须**继续抛出**，
不能像普通异常那样吞掉。否则协程取消会被当成"请求失败"，表现为"取消搜索后界面闪一下错误"。

### 2.5 编码层的差异

| 项 | 说明 |
|---|---|
| `obj.optString("key", "")` vs ArkTS 的 `?? ''` | Kotlin 的 `optString` 对缺失键返回默认值、对 JSON `null` 返回字符串 `"null"` —— 故所有解析点统一走 `optString(..., "")` 且**不直接拼进 UI**，避免把 `"null"` 显示成片名 |
| Base64 | ArkTS `util.Base64Helper` → `java.util.Base64`；独播库的"每 10 字符反转 + `.`→`=`"自定义混淆逐字保留 |
| AES 密钥长度 | ArkTS 的 `'AES128'/'AES256'` 字面量保留为 `alg` 参数，由 `Aes.keySpec()` 换算实际密钥长度（取前 16/32 字节） |
| protobuf varint | ArkTS 用 `Math.pow(2, shift)` 累加，Kotlin 用 `Long` 移位；**wire type 5 必须跳过而非中断**（桔子 f10 是 fixed32，中断会丢后面所有分集） |
| Java LCG | ArkTS 用"倍增取模"避免 float64 精度损失；Kotlin 用 `Long` + 同款倍增，因为 `25214903917 × (2^48-1) ≈ 7.1e24` 仍溢出 64 位 |

## 3. 有意保留的原工程缺陷

移植的纪律是：**行为契约不动，把观察记下来**。以下三条是源工程已知的、本次未修的问题，
保持原样并在测试里固化，避免"移植时顺手改了但没人知道"。

| 项 | 现状 | 为什么不顺手改 |
|---|---|---|
| `parseYear` 的注释与代码不符 | 注释写"取开头连续四位"，代码是"扫过前置非数字再取数字"。代码为准 | 改代码要同步改验收记录；改注释又会让两份文档对不上。先在测试里固化代码行为 |
| `aggregateNotice` 的混合态归类 | 「1 个失败 + 1 个无数据」→ 报「都没有这部片」 | 改它破坏 NFR-008 已验收的两分法；先固化再评估 |
| 投屏链路真机未验证 | 通道代码已接通，但无设备可跑 | 补真机验证需同一局域网内的 Cast 接收端 + 装了 Play 服务的设备；属独立工作，不写「已验证」 |

## 4. 与源工程的数据兼容

**不承诺跨平台数据互通**：鸿蒙用 preferences 文件、Android 用 SharedPreferences XML，
两者的**键名与载荷结构一致**（`favorites`/`history`/`search_history` 等，载荷是同一个版本信封），
故理论上可写出一个转换脚本；但产品上无此需求，本移植未提供，也未测试。

版本信封的 `CURRENT_VERSION = 1` 与源工程一致；若将来两端并行演进，需先约定版本号分配。
